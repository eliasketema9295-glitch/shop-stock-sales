01 Architecture

Four layers. One rule: only the API touches the database.

The MCP server is just another API client. It holds no credentials, no SQL and no stock logic — so every business rule applies to the AI exactly as it does to a human cashier. Pick a layer to see what it owns.

Claude Desktop

MCP client · user surface

The only place a human types. It sees seven tool signatures and none of the system beneath them — no database URL, no API key, no SQL.

  • Natural language in, tool calls out
  • Cannot bypass a tool to reach Postgres
  • Every write arrives as a preview first
The MCP server never touches the database. It is a client — nothing more.

02 Safety by default

The AI can't sell you what you don't have.

An MCP tool cannot pause and wait for a human confirmation, so every write takes two calls. The same protocol covers record_sale and restock_product.

01

Preview — nothing is saved

Called without confirm. The API prices the basket, projects stock, writes an audit row and returns a short-lived token bound to those exact items.

POST /sales/preview
→ { token, total, projectedStock }
// 0 rows changed
02

Confirm — one transaction

Called again with confirm: true, the token and an idempotency key. Stock is re-checked under a row lock, then the sale and its movements commit together — or not at all.

POST /sales/confirm
→ BEGIN · lock · insert · COMMIT
// all or nothing
03

Replay — safe retries

If the same key arrives twice — a retry, a dropped connection, a model repeating itself — the API returns the original result. No second sale is ever created.

same idempotencyKey
→ 200 · replayed: true
// stock unchanged

04 MCP tools

Seven tools Claude can call.

Five read-only, two that write. Each signature is deliberately boring: narrow arguments, explicit units, and a description that tells the model exactly what it must confirm first.

7 of 7 tools
search_products read

Finds products by name or SKU. Returns price, stock and reorder level.

query string · limit? 1–50
check_stock read

One product's stock, with LOW / OUT flags and the reorder point attached.

sku string
low_stock_report read

Everything at or below its reorder point, with the supplier to call.

threshold? integer (default 10)
sales_summary read

Revenue and order count for a period, grouped by day or by product.

from ISO date · to ISO date · groupBy day|product
top_selling_products read

Best sellers ranked by units or revenue, over any date range.

metric units|revenue · limit? 1–20
record_sale writes

Records a sale and reduces stock. Preview first — writes only with confirm: true.

items [{sku, qty}] · confirm false · token? · idempotencyKey?
restock_product writes

Adds received units to stock. Add-only — it cannot reduce or overwrite.

sku string · quantity 1–500 · confirm false
the rule behind all seven

No write without a preview, a token, and a confirmation.

06 Source

How the magic actually happens.

Three files tell the whole story: the transaction that can't half-commit, the schema that records every movement, and the translator that never learns SQL. 

// api/src/routes/sales.ts
// Preview writes nothing. Confirm writes once. Replay writes never.
app.post('/sales/preview', async (req, reply) => {
  const { items } = saleSchema.parse(req.body);
  const rows = await db.select().from(products)
    .where(inArray(products.sku, items.map((i) => i.sku)));

  const total = items.reduce(
    (sum, i) => sum + i.qty * priceOf(rows, i.sku), 0,
  );
  const token = signPreview({ items, total }, { expiresIn: '60s' });

  await audit.log('sale.preview', { items, total });
  return reply.code(201).send({ token, total, projectedStock });
});

app.post('/sales/confirm', async (req, reply) => {
  const { token, idempotencyKey } = confirmSchema.parse(req.body);

  // A retry is not a new sale.
  const prior = await sales.findByIdempotencyKey(idempotencyKey);
  if (prior) return reply.send({ ...prior, replayed: true });

  return db.transaction(async (tx) => {
    const claim = verifyPreview(token);          // 401 if expired
    const sale = await insertSale(tx, claim, idempotencyKey);
    await moveStock(tx, sale);                   // lock, check, decrement
    return reply.code(201).send(sale);
  });
});
// api/src/db/schema.ts
import { pgTable, uuid, text, integer, timestamp, numeric } from 'drizzle-orm/pg-core';

export const products = pgTable('products', {
  id: uuid('id').primaryKey().defaultRandom(),
  sku: text('sku').notNull().unique(),
  name: text('name').notNull(),
  price: numeric('price', { precision: 10, scale: 2 }).notNull(),
  stock: integer('stock').notNull().default(0),
  reorderAt: integer('reorder_at').notNull().default(5),
});

export const sales = pgTable('sales', {
  id: uuid('id').primaryKey().defaultRandom(),
  idempotencyKey: text('idempotency_key').notNull().unique(),
  total: numeric('total', { precision: 10, scale: 2 }).notNull(),
  createdAt: timestamp('created_at').defaultNow().notNull(),
});

// Append-only. Stock is never edited; it is derived from movements.
export const stockMovements = pgTable('stock_movements', {
  id: uuid('id').primaryKey().defaultRandom(),
  productId: uuid('product_id').references(() => products.id),
  delta: integer('delta').notNull(),
  reason: text('reason').notNull(),  // 'sale' | 'restock' | 'correction'
  saleId: uuid('sale_id').references(() => sales.id),
  createdAt: timestamp('created_at').defaultNow().notNull(),
});
// mcp/src/index.ts — the translator, not the brain
const api = (path: string) =>
  fetch(`${API_URL}${path}`, {
    headers: { 'x-api-key': process.env.SHOP_API_KEY! },
  }).then((r) => {
    if (!r.ok) throw new Error(`${r.status} ${r.statusText}`);
    return r.json();
  });

server.tool(
  'check_stock',
  'Stock level for one product. Read-only. Use before record_sale.',
  { sku: z.string().describe('Product SKU, for example CER-01') },
  async ({ sku }) => {
    const p = await api(`/products/${sku}/stock`);
    return {
      content: [{
        type: 'text',
        text: `${p.name}: ${p.stock} in stock (reorder at ${p.reorderAt})`,
      }],
    };
  },
);

// No Postgres import. No SQL. No stock arithmetic. Just HTTP.

TypeScript strict throughout. Zod parses every boundary; the database is the only source of truth; the MCP server is stateless and restartable.
